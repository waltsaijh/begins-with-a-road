# Begins With a Road — 3D Modeling

**遠看是一幅漂亮的迷宮，中看是清晰的戰術符號，近看是結構精緻的微縮建築。**

## 開始前

- 先讀專案根目錄的 [AGENTS.md](../../../AGENTS.md)、[架構](../../../docs/architectures.md) 及目標資產相關系統文件；核對 Git 狀態與實際場景覆寫。
- 每次建模先讀 [專案實測契約](references/project-spec.md)，核對目標 TowerDefinition、TilePreset、模型與掛載程式；其中數值是有日期的快照，變動時以目前程式／Resource 為準。
- 實際操作前讀 [Blender 與 Godot 流程](references/blender-workflow.md)。只要求規格、Skill、讀取或評估時，停在文件／讀取；不要順便生成模型。
- 建模前簡述目標的用途、主要輪廓、占格、正面、可動零件、升級插槽及交付路徑。資訊可由專案確認就直接採用，只有會改變設計的缺口才詢問。

## 美術設計原則

以 Isle of Arrows 的迷宮秩序、Thronefall 的清楚量體作方向參考，建立本作自己的幾何語彙，不複製辨識性資產。

| 觀看距離 | 成功條件 | 決策方式 |
| --- | --- | --- |
| 遠景 | 道路連續、建築群形成有節奏的迷宮 | 先看整張地圖的留白、密度、輪廓與遮擋 |
| 中景 | 無名稱、無顏色也能辨認塔種與攻擊方向 | 先做純灰／剪影，確認一個主形加一個功能特徵 |
| 近景 | 看得出受力、轉動、裝填與接合方式 | 只增加能解釋結構的幾何 |

- 保持極簡、符號化、低面數。主要量體用方柱、楔形、切角盒、稜柱、低分段圓筒及明確的負空間組成。
- 不同塔不能只換顏色、旗幟或表面小配件；主要剪影、長寬比例、重心或武器配置必須不同。既有六塔的功能辨識見專案契約。
- 建築與道路共享格子節奏；避免遮住岔路、端點、路肩凹槽及相鄰塔的主要輪廓。鏡頭可繞場景旋轉，不能只在單一方向成立。
- 細節優先序：主量體 → 功能構件 → 接合。新增零件需能回答「承重、發射、裝填、轉動、防護或入口」中的具體用途；不為填空加鉚釘、花紋、隨機破損或裝飾線。

## 幾何造型規範

- 單格指占地模組，不代表所有塔都是 1×1；以實際 footprint 聯集建模，L 形不能用完整外接矩形填死空缺。
- 根原點在邏輯錨點的承載平面；多格模型的質心／砲座可偏離原點。不得為置中美觀搬動錨點或攻擊中心。
- 固定底座、武器、瞄準軸、後座機構與可替換升級件分組；只合併同一運動／可見性群組內的靜態網格。
- 切角、凹槽、開孔和機械接合用真實幾何；有功能的孔要有內壁與可讀厚度，不能用黑貼片假裝孔洞。遮蔽且沒有影響陰影的內部細節可以省略。
- 以 flat shading 與明確折線為主；圓筒先試 6–12 邊、倒角先試 1 段，只有實際遊戲鏡頭出現不良輪廓才增加。這是製作起點，並非既有引擎限制。
- 不設未量測的硬性三角形預算。記錄匯出後三角形、頂點、mesh／surface／材質數；先減少看不見的細節與零碎 surface，再以遊戲呈現決定取捨。
- Lv1 保留完整可讀功能；Lv2／Lv3 用可替換武器、支架或防護結構強化原輪廓，不能靠顏色暗示新射程／新兵種。只預留插槽，不自行實作新升級規則。

## 材質與色彩規範

- 每棟以一個主色家族為主，少量中性結構色及功能強調色。用面積與明度形成主從，避免等面積的多色拼塊；無紋理、無隨機逐面色差。
- 從現有道路／石地／塔色盤與目標 TowerDefinition.accent_color 選色。暖石地與藍灰陰影的環境下仍須看得清楚，亦要做灰階檢查。
- Blender 用簡單 Principled BSDF 常量色、Opaque、非金屬、偏高粗糙度；材質節點按 type 查詢，不按可翻譯名稱查詢。
- 不預設使用貼圖、程序化噪聲、normal／bump、透明、發光、複雜 shader 或額外外部素材。功能確有需要才另行說明，並維持 Compatibility／單執行緒 Web 方向。
- GLB 的 PBR 材質是交換資料，**不是**本專案 `solid_color` 網格格式。未經離線轉換與檢查，不能直接換上共用 shader；細節見流程文件。

## 工作流程與交付

1. 盤點 Blender 連線與場景，隔離本資產的 collection；先保存可重跑的 Python，再透過 MCP 分階段執行。
2. 先做尺寸與剪影，再功能幾何，再少量材質；依專案契約從正式正交鏡頭、最遠縮放、四向及密集道路構圖檢查。
3. 保存 `.blend`、建模／匯出 Python 及資產規格記錄；以 GLB 交付 Godot，來源放在不會觸發 `.blend` 自動匯入的位置。命名與路徑見流程文件。
4. 任務包含 Godot 接入時，使用可重匯入的 `.tscn` 外觀包裝層，保留現有掛載／砲口契約。先檢查是否經 TowerBodyVisual；現有系統無法直接套用時，交付模型並指出需要的接入工作，不藉建模改寫遊戲系統。
5. 回報來源、GLB、wrapper（如有）、規格、實際驗證及未執行項目。Blender 預覽通過與 Godot 正式接入通過分開記錄。

## 模型檢查清單

- [ ] 正交遠景先辨認道路與塔種；灰階／剪影可辨識；四向旋轉及密集擺放仍清楚。
- [ ] 每個主要零件都有功能，切角／凹槽／開孔為幾何，沒有無功能裝飾或多餘細分。
- [ ] 實際 footprint、邏輯錨點、1 格尺度、底面高度及正面正確；相鄰格與路口未被視覺封死。
- [ ] 根比例 1、無負縮放／非預期鏡像；法線朝外；無重面、z-fighting、漂浮、缺面與遺留布林切割物；有意開放的邊界有記錄。
- [ ] 固定件、瞄準、後座、砲口、艇身及升級件各自保留必要 pivot／層級，未合併成無法運動的一件網格。
- [ ] 單主色、少量輔色、不靠紋理細節辨識；Godot 材質與需要的頂點通道一致。
- [ ] Python 重跑兩次不產生重複物件、材質或累積變換，不影響其他資產；`.blend` 與腳本可重建交付物。
- [ ] GLB 只含目標資產，含所有交付等級件，無預覽相機／燈／格網／外部依賴；記錄匯出選項與幾何統計。
- [ ] 若已接入：重匯入保留 wrapper 的節點路徑／標記，正式與放置預覽顯示一致；瞄準、後座、升級及空艇巡航按本次範圍驗證。
- [ ] 明列未接入／未渲染／未測 Web 等限制，不把歷史測試當作本次結果。
