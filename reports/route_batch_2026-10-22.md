# 延後除錯摘要、批次配額與共用座標量測（2026-10-22）

同日後續的候選運算 C++ 搬移，見[獨立對照報告](native_candidates_2026-10-22.md)；本頁保留批次配額實作當次結果。

本次比較 `experiment/reduced_graph` 的 `27f4ddc`（已包含去環）與其後的三項優化，不是和去環之前的 main 比較。測試使用獨立實例及複製的兵種設定，未修改正式關卡、兵種或塔的 Resource 數值。

## 實作與結果一致性

1. 正式 `plan_for` 只建立輕量摘要。最終候選的節點／邊聯集、steps、directions 及數量，改由 `debug_summary_for` 明確要求時才建立並快取；計畫失效時清除。原生探索 API 不變。F1 仍從當波完整行程繪圖，不要求這份摘要。
2. 每個兵種／入口批次準備一次整波配額。相同候選只建立一次獨立於計畫快取的路線快照，各敵人保存各自的字典、數值與移動進度，不再逐名重查／複製計畫摘要。
3. 同一次波次建立中，相同完整路徑共用唯讀世界座標；下一次建立使用新快取，避免地圖 transform 過期。排程內部的 Enemy.follow 共用該座標，對外呼叫仍保留防禦性複製。每幀移動方法沒有新增工作。

本次負載的 256 名敵人需要 211 組不同的世界座標，從原本逐名轉換 256 次降至 211 次。快照／配額排程的前後比較逐欄一致；六次渲染測試中，按 enemy_id 排序的路線 index／cells／score／selection_probability 指紋均為 `b653df64fcf7dadce7bc675aac826a8f9d304f333d37fecd49029b68283aa8ab`。各計畫候選條目維持 1,451，重複格子候選維持 0。

## 環境與負載

沿用去環量測的 32×32 合成地圖：801 格道路、16 個房間、窄連接及區域內障礙，16 座 Sentry，91 個 vertex／19 個 region。256 混兵為 Soldier 86、Quickfeet 85、Heavy 85，同時出生；測試副本生命 1,000,000、速度倍率 0.45，基準速度 2.5，確保整段量測維持 256 名存活。

Windows、Ryzen 5 4600H、7.42 GiB RAM、RTX 3050 Laptop GPU，Godot 4.7.2 stable editor runtime／template_debug GDExtension、Compatibility、NVIDIA 驅動 591.86。實際渲染為 1280×800、VSync 關閉、FPS 不設上限、F1/F2 關閉；相機完整取景，near=0.1、far=150，已檢查截圖。

- 冷建池：全新 native planner、prepare 與三兵種計畫；headless 僅量 CPU，暖機一對後，交錯前後順序各 12 次。
- 排程：同樣地圖、快取已準備的計畫，暖機一對後交錯各 12 次；僅量完整配額／行程快照／世界座標／出生刻度排程，不包含模型生成，也不拿來推估 FPS。
- 實際渲染：前後各三次，3 秒暖機、12 秒 wall 幀間隔取樣；每次開始與結束均存活 256 名。以下表格列各次統計的中位數及範圍，不是將所有幀混在一起計算。

12 次試驗的中位數取中間兩個排序值的平均；原始樣本未變，已修正當次工具最初採上中位值的彙總欄位。

此次重新量測的絕對數字與前一份去環報告不同；未固定 CPU 時脈與背景負載，不應用兩份報告的單點直接相減。以上收益採本次交錯 A/B 的結果。

## 實際渲染與生成停頓

| 指標（三次結果的中位數） | 優化前 | 優化後 |
| --- | ---: | ---: |
| 平均幀時間 | 11.87 ms | 12.10 ms |

| 各次最大幀時間範圍 | 19.60–20.19 ms | 18.84–24.81 ms |
| 256 名行程排程（實際渲染程序內） | 17.27 ms | 14.50 ms |

本輪未測得穩態 FPS 提升，P99 也較高。三項改動集中在建池與波次建立，每幀移動流程未變；三輪短測不足以判定尾端差異的原因。整批模型／動畫／血條建立及首幀等待仍有明顯停頓，本次沒有證明這部分改善，不能將排程省時解讀成模型生成也省時。
