# P99 幀時間差異調查（2026-10-22）

## 結論

先前 C++ 搬移 A/B 的 P99 19.04 → 27.20 ms，不能作為這次搬移造成每幀回退的證據。後續固定工作量對照查到：測試期間 CPU 有效執行速度／效能計數會明顯變動，既有動畫、座標提交、避讓與繪製 CPU 成本一起被放大。沒有發現候選 C++ 搬移增加每幀工作；保留原生建池優化，不為這份量測改遊戲規則。

主要證據：

1. 原先 A/B 本就使用同一份原生 DLL；差別是候選後處理走腳本或 C++。23 輪固定進度測試的完整路線及最終敵人位置／移動距離／血量／護盾指紋一致；每一幀的避讓候選檢查數與塔攻擊計數序列也一致。
2. 有呼叫計數的 22 輪中，取樣開始／結束皆為 plan_for=9、代表抽取=3、批次配額=3，增量全為 0。較慢的幀沒有重新建池、重評分、建立 CDF 或分配行程。
3. 不改程式、同走新版 C++ 建池的四輪校準測試，P99 為 32.29、31.10、16.21、15.66 ms。這個同版本波動已大於先前聲稱可能回退的 8.16 ms。
4. 同一個固定 16,384 步整數運算的中位耗時，在較快新版兩輪為 113 µs，較慢新版兩輪為 166／154 µs；這個校準不讀取路線、敵人或遊戲資料。六輪校準測試的校準平均耗時與平均幀時間相關係數約 0.993；這是診斷線索，不是以六個點推論通用效能模型。
5. 同步 Windows PDH `% Processor Performance` 記錄顯示：freq-after-1 的中段 150 幀窗口，當下核心有效效能計數平均約 93.6%、固定校準平均 155.5 µs、平均幀 17.97 ms；同一輪最後 150 幀恢復約 118.0%、122.5 µs、11.45 ms。較快舊版窗口的計數約 118%。這是在同一份新版程式內觀察到的環境執行速度變化。

能確認的是處理器有效執行速度波動與既有 CPU 熱點；未再把功耗／溫度限制和其他程序競爭逐一分離，也沒有足夠證據把慢幀歸咎於某個背景程序。未調整 Windows 電源、程序優先權／親和性、GPU 設定或關閉使用者程式。

## 為什麼舊量測不夠判因

- Godot 的 Performance.TIME_PROCESS／TIME_PHYSICS_PROCESS 是定期更新的監視統計，舊工具每幀重複讀取它們，不能把這些重複值當成那一個慢幀的更新／物理耗時。
- 原來以實際 3 秒暖機、12 秒取樣，各輪幀數、模擬步數及末端戰況未完全對齊。路線指紋相同只能證明走法相同，不能證明每幀處理的是相同狀態。
- 新增直接 Time.get_ticks_usec 探針，依 process_priority 量測整段節點更新、戰鬥、模型／動畫／避讓、頭頂狀態，以及 RenderingServer 的 pre/post draw。另開啟 viewport 的 CPU／GPU 渲染計時；不再以監視統計代替逐幀計時。
- 用 --fixed-fps 60 固定模擬 delta，180 幀暖機、600 幀取樣；這個參數不是實際 60 FPS 上限，wall 幀時間仍直接量測且不限速。檢查每輪 600 次實際 draw、256 存活、相同路線、最終戰況與逐幀工作計數。前後版本交錯執行，保留所有有效輪次，沒有因慢而剔除樣本。

## 相同新版程式的對照

以下四輪使用同一個帶暫時計時介面的 debug DLL、相同場景與固定模擬進度，遊戲路徑全部走新版 C++；sham 只是測試標籤。校準迴圈也相同。

| 輪次 | 固定 CPU 校準中位數 | 平均幀時間 | P99 |
| --- | ---: | ---: | ---: |
| cal-after-1 | 166 µs | 18.43 ms | 32.29 ms |
| cal-after-2 | 154 µs | 16.34 ms | 31.10 ms |
| sham-new-A | 113 µs | 11.54 ms | 16.21 ms |
| sham-new-B | 113 µs | 11.31 ms | 15.66 ms |

同時也能在舊版重現高尾端：probe-before-4 P99=26.57 ms、cal-before-1 P99=26.33 ms。各輪統計保持獨立；不把不同探針／校準負載的所有幀混合成一個 P99，也不把較快輪次宣稱為本次修正收益。

## 慢幀在哪裡

在較穩定的 clock-before-2，模型段平均約 3.57 ms；86 次避讓求解（600 幀中）使部分幀的模型段升到約 7–8 ms。避讓是既有按間隔執行的工作，沒有隨 C++ 搬移增加。

較慢區段中，動畫／姿態、偏移與 transform 提交、頭頂狀態和 draw CPU 耗時會一起上升；例如 clock-after-1 最慢六幀的模型段平均約 10.50 ms、draw 段約 11.73 ms，而 viewport GPU 約 2.62 ms。clock-before-1 也有相同型態的 CPU 尖峰。這不是單純 GPU 填滿，也不是去環在移動時重跑。

Windows GetThreadTimes／QueryThreadCycleTime 與記憶體計數用於交叉核對。GetThreadTimes 有約 15.625 ms 量化，不能把每一幀的小差值當高精度 CPU 時間；慢區段仍可見主執行緒實耗增加，而不是一律解讀成等待。固定校準與 PDH 資料提供額外獨立證據。兩組工作集均約 281–282 MiB，沒有觀察到足以支持候選快取膨脹／持續成長的差異；這不是長時間無洩漏證明。

## 收尾與驗證

- 暫時加入的 Windows 計時介面已完全移除。route_planner.cpp／hpp 已逐位元還原為調查開始時的 C++ 搬移版本，重建 Windows debug 擴充成功；原 Windows release、Web debug／release 未在本輪修改。
- 額外檢查確認執行期不再暴露 diagnostic_clock；native_candidates 與 route_batch 回歸再跑通過，涵蓋 286 條候選、完整資料順序、CDF／256 配額及快照獨立性。
- 移除臨時計時介面後，用正式擴充執行修正的逐幀量測：clean-native-1 平均 11.62 ms、P99 16.66 ms、600 次 draw／256 存活，路線及戰況指紋仍相同。這只是清理後驗證，不是遊戲演算法修正前後的收益比較。
- 本輪沒有變更遊戲運算邏輯、正式 Resource、波次或移動路徑；修正的是量測方式與報告判讀。

## 環境、次數與原始資料

沿用 32×32／801 道路格／91 vertex／19 region、16 塔、256 混兵，Quickfeet path_base_cost=0.25，測試副本生命 1,000,000、速度倍率 0.45、波次速度 2.5。Ryzen 5 4600H、RTX 3050 Laptop GPU、NVIDIA 591.86、Godot 4.7.2 Compatibility，1280×800、VSync 關閉、不限實際 FPS、場外視窗，camera near=0.1／far=150。600 次 draw 計數確認取樣期間確實繪製。

共 23 輪／13,800 個取樣幀：probe 8 輪、Windows 執行緒計時 clock 4 輪、CPU 校準 cal 4 輪、同新版 sham 2 輪、同步 PDH freq 4 輪、清理後正式擴充 1 輪；各輪皆另有 180 幀暖機。第一輪未加呼叫計數，其餘 22 輪有。沒有 Web 或其他 GPU 量測。

全部原始資料在 `.godot/test-results/navigation/p99_probe/`：各 tag JSON 含逐幀資料，calibration_summary.json、investigation_summary.json 為彙總，cpu_performance.json 為約每 0.5 秒的各核心 PDH 記錄；依系統 Unix 時戳與當幀核心索引對齊。PDH 為區間平均，不能把它當成每幀瞬時頻率。

一次性固定進度／直接計時工具、腳本探針、原生診斷版與原始碼備份、PDH 收集工具均已依清理要求移除；正式 DLL 不提供臨時計時介面。原始樣本、log 與還原建置紀錄保留於本機 `.godot/`，本頁不提供已移除工具的重現入口。
